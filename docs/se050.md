# SE050 driver

Status: written and compiled on a PC, all 1066 PC tests green.
**Nothing has run on hardware.** The parts for the test bench are ordered
and on their way.

## What the driver does

The SE050 is the secure element on the I2C bus next to the nRF52840. Every
secret the device holds lives in it and never leaves it. This driver is the
only code that talks to it.

Three layers, each testable on its own:

| Layer | Files | Job |
| --- | --- | --- |
| Bus | `se050_bus.h` | read, write, wait — the only thing that touches hardware |
| T=1' | `se050_t1.c`, `se050_crc.c`, `se050_t1_wire.h` | frames, checksum, retry, timeouts, chaining |
| APDU | `se050_apdu.c`, `se050_tlv.c`, `se050_cmd.h` | build commands, read answers, translate status words |
| SCP03 | `se050_scp03.c` | the encrypted channel — mandatory, not optional |
| Contract | `se050.c` | the functions in `apps/firmware/include/osk_se050.h` |
| Contract: RSA | `se050_rsa.c` | key, public part, sign, decrypt |
| Contract: counters | `se050_counter.c` | monotonic counters, forward only |

The bus is a narrow interface on purpose: the same driver code runs against
the nRF52840's I2C peripheral on the device and against a test bus on a PC.
That is how the tests exist at all.

`se050_platform.h` holds the two things the driver cannot know by itself —
which bus to use and where the SCP03 keys come from. On the device the board
and vault layers fill those in; in the tests `test_contract.c` does. There is
deliberately no default implementation: a missing one breaks the link rather
than quietly running with a key of zeros.

### SCP03 is not a feature

Without it, anyone who probes the two I2C lines on the board sees every
command in the clear — which is precisely the hole the SE050 exists to close.
So `osk_se050_open()` fails if the channel cannot be built, and every command
after that is encrypted and authenticated in both directions. A wrong R-MAC
tears the channel down instead of being retried.

### Crypto is not written here

AES and AES-CMAC come from an audited library, never from this repo:

- on the device: PSA Crypto from the nRF Connect SDK (`se050_crypto_psa.c`)
- in the PC test build: Windows CNG / bcrypt.dll (`se050_crypto_cng.c`)

`se050_crypto.h` is the seam between them. It says what SCP03 needs and
nothing more.

### The frame layer now follows a freely available specification

The T=1' frame format was the one part of this driver that could not be
looked up: NXP's own description, UM11225, is behind an NXP account login.
Those values were derived from ISO/IEC 7816-3 and carried as explicitly
unconfirmed.

**That is resolved, and not by getting UM11225.** The SE051 data sheet
(Rev. 1.4, sections 1 and 2.1) states that the chip supports **two** T=1
over I2C protocols and **detects from the prologue of the first block**
which one is in use:

- NXP SE05x T=1 Over I2C (UM11225) — login only
- **APDU Transport over SPI/I2C, GPC_SPE_172** — GlobalPlatform, published
  freely

So the driver now implements the GlobalPlatform one. That is better than
merely available: this repository is public and MIT, and a driver whose
frame layer can only be checked against a document behind a vendor account
cannot be reviewed by anyone outside. Now it can.

**What the switch changed.** The old values were derived, not read, so the
comparison is worth recording:

| | derived from ISO 7816-3 | GPC_SPE_172 | |
| --- | --- | --- | --- |
| PCB bit layout (I/R/S, N(S), M, N(R), error bits) | as written | same | correct |
| S(RESYNCH), S(IFS), S(ABORT), S(WTX) | 0x00, 0x01, 0x02, 0x03 | same | correct |
| interface reset | `IF_SOFT_RESET` 0x0F | `S(SWR)` 0x0F | same value |
| end of session | `END_APDU` 0x05 | `S(RELEASE)` **0x06** | was wrong |
| read chip parameters | `GET_ATR` 0x07 | `S(CIP)` **0x04** | was wrong |
| chip reset | `CHIP_RESET` 0x06 | does not exist | was invented |
| LEN field | 1 byte | **2 bytes, big-endian** | was wrong |
| CRC byte order | little-endian | **big-endian** | was wrong |
| NAD | 0x5A / 0xA5 | 0x29 / 0x92 recommended | both valid under the rules |

The bit layout and half the S-block codes were right; the frame shape was
not. That is roughly the outcome one should expect from a careful
derivation, and exactly why it was carried as unconfirmed rather than
built upon as fact.

Parameterising the values paid for itself here. The CRC byte order lives in
`SE050_CRC_LSB_FIRST`, the tests read that switch instead of assuming an
order, and flipping it moved the tests with it rather than breaking them.

### Two things about this are still open

1. **The version.** The SE051 data sheet cites "APDU Transport over
   SPI/I2C v1.0" (January 2020). What is implemented against is
   **1.0.0.34, Public Review, April 2025** — same document reference,
   later edition. "Public Review" means it could still change. The frame
   basics are very unlikely to have moved, but that is a judgement, not a
   fact, and it is marked in `se050_t1_wire.h`.
2. **The automatic detection is a promise on paper.** The data sheet says
   the chip picks the protocol from the first prologue. On hardware that is
   a measurement — and it is the *first* one, because if it does not hold,
   this whole layer is wrong and UM11225 is needed after all. It is first in
   the measurement plan below.

### What to measure first, in order

The order matters. The first two questions decide whether the layer works at
all and whether the project's upper stages are buildable; everything after
that is detail. Each is one experiment with a clear pass or fail.

**1. Does the chip talk to us?** Send `S(SWR request)` and look for an
`S(SWR response)`.

If yes, the GlobalPlatform framing was accepted and the auto-detection the
SE051 data sheet promises works. If the chip stays silent or holds the clock
line, it did not — and the fallback is UM11225, which costs one file,
`se050_t1_wire.h`, because nothing else uses its values directly.

**2. What is this part actually allowed to do?** Run `osk_se050_open()` and
write down the feature bitmap and the free memory.

This is second rather than last **because it decides which stages of the
project can be built at all.** The bitmap is set at the factory and cannot be
changed afterwards. If `CONFIG_EDDSA` and `CONFIG_DH_MONT` are clear and
`CONFIG_FIPS_MODE_DISABLED` is 0 — the combination the FIPS policy documents
for a real SE051 — then Ed25519, X25519 and ECDH are all unavailable, and
three planned capabilities are gone before a line of their code is written.
That is a first-day fact, not a stage-eight surprise. `osk_se050_free_memory()`
in the same run gives the credential capacity.

**3. Is FIPS mode actually switched on?** `IDENTIFY` reads the DF28 file from
the card manager (FIPS security policy, section 1.1.1):

```
80 CA 00 FE 02 DF 28 00
```

Tag `05` is the FIPS status: `00` not active, `01` active. Tag `03` is the
platform version, `02` the patch version, `08` the ROM ID — together they
prove what actually arrived rather than what the packaging said.

Worth running even though step 2 already read `CONFIG_FIPS_MODE_DISABLED`,
because the two answer different questions: the bitmap bit says FIPS mode is
*possible* ("the device **might** operate in FIPS approved mode", AN12413
Table 5); tag `05` says whether it is *switched on*.

It is deliberately **not** built into the driver. `IDENTIFY` is a card manager
command, not an applet one, and whether it answers after the applet has been
selected is the same unresolved level question as the one noted for
`PUT KEY`. As a one-off diagnostic it costs nothing to get wrong; as a code
path it would be another unverifiable assumption. The driver's own guard uses
the bitmap, which is what AN12413 ties the ECDH behaviour to.

**4. Does `S(CIP request)` return a parseable CIP?** That yields the real BWT
and IFSC instead of the defaults of 300 ms and 8 bytes.

**5. Does `S(IFS request)` with a 2-byte value get accepted?** The
specification allows 1 or 2 bytes; the driver sends 2.

**6. Does a chained command survive?** Send more than one IFSC worth and check
the response comes back whole.

**7. Timing.** Measure the real answer time of the slowest operation (P-384
key generation) against the BWT the chip reported.

## What is verified and what is not

Four levels apply (house rule): written / compiled / in the image / run on
the device. This driver has reached **compiled**, plus PC tests.

### Verified against outside, published values

- **AES, AES-CBC, AES-CMAC** against NIST SP 800-38A (F.1.1, F.2.1) and
  SP 800-38B (examples 1–3, including the short final block). If these were
  wrong, every SCP03 test above would be worthless, so they are checked first.
- **CRC-16/X-25** against the standard check value 0x906E for "123456789".
  That value distinguishes X-25 from the other CRC-16 variants.
- **The layout of the SCP03 derivation input** against the three worked
  examples printed in AN12413 section 3.2
  (`00000000000000000000000400008001` and the S-MAC/S-RMAC equivalents).
  Without that anchor the field order from Amendment D 4.1.5 would only be
  checked against itself, and a swapped field never shows up in a round trip.

### Verified only against itself

- **The full SCP03 session.** GlobalPlatform publishes no test vectors for
  Amendment D, and there is no hardware. `test_contract.c` runs
  `osk_se050_open()` against `se050_sim.c`, a stand-in for the chip that
  verifies the driver's C-MAC and builds its answers the way the chip is
  documented to. Driver and stand-in therefore read the specification the
  same way — **if both misread the same sentence, they still agree.** This
  proves the layers fit each other, not that they fit an SE050.
- **Every T=1' frame.** Same caveat. The frame *values* are no longer
  guesses — they come from GPC_SPE_172 — but whether the chip accepts this
  protocol variant at all is measurement #1 above.

### Not verified at all

- Anything on real hardware. No board exists.
- `se050_crypto_psa.c` is written but compiled **nowhere**: it needs the
  nRF Connect SDK, which is not on the build machine. It is the one file here
  that has not even reached "compiles".
- Timing. The timeouts in `se050_t1_wire.h` are generous guesses; the test bus
  fakes its clock.
- The I2C edge-timing requirement from errata I2C.4 (SCL must change before
  SDA). That is a board and pin-driver matter, not this driver's.

Two ways, and both are run before every commit here:


```bash
make -C apps/firmware/test/se050
```

1066 checks, all green either way. Warnings are errors (`/W4 /WX` and
`-Wall -Wextra -Werror -Wconversion -Wshadow`).

The two paths exist because the CI runs `make` with gcc on Linux, where
Windows CNG does not exist. So there are three crypto backends behind the one

Keeping both was worth it rather than tedious: gcc rejected a helper that

`tools/check.py` counts. Until that line existed the suite was invisible to
the CI — `check.py` reported `firmware/tests` as skipped, so the then 902 checks
were green locally and simply never ran there. They now show up as
`firmware tests/se050 ok — make (1066 Faelle)`.

## Correction: an AESKey session needs CreateSession and ProcessSessionCmd

The first version of this driver sent `INITIALIZE UPDATE` straight after
selecting the applet and then sent each command on its own. **That would not
have worked on hardware.** AN12413 section 3.6.3.2 spells the flow out:

1. `CreateSession(id of the authentication object)` → 8-byte session id
2. `ProcessSessionCmd(id, SCPInitializeUpdate)`
3. `ProcessSessionCmd(id, SCPExternalAuthenticate)`

and from then on **every** command travels inside a `ProcessSessionCmd`. The
SCP03 protection sits on the inner command; the outer envelope is in the
clear. There is also no anonymous channel — a session always runs against a
named authentication object, which is why `se050_platform.h` now has a third
hook for that object's id.

This was found while rebuilding the PIN path, because the PIN session uses the
same mechanism. It is corrected, and `test_contract.c` now asserts that
`CreateSession` ran and that it named the right object — so a regression to the
old shape fails the tests rather than waiting for hardware.

Two sessions is the hard limit (AN12413 Table 16, `MAX_NUMBER_OF_SESSIONS`).
The device channel holds one and the PIN check borrows the other for the
duration of the check, so the budget is exactly spent. Anything else that
wants a session has to wait for one.

## The factory keys are published — first-run rotation is mandatory

**SCP03 with factory keys protects nothing.** The default Platform SCP keys
are printed in the clear in AN12973 Table 6 — ENC, MAC and DEK, per variant
and per fabrication lot (OEF ID). Anyone who downloads that free document can
decrypt the I2C traffic of a device left in its factory state. This was
verified against the document directly, not taken on trust; the values are
deliberately **not** reproduced in this repo, because the driver never needs
them hard-coded — the platform hook supplies whatever is current.

Two things are therefore required at first run, and **neither alone is
enough**:

1. **`osk_se050_rotate_scp_keys()`** for key set 11 **and** key set 12.
   AN12973 section 2.3 describes set 12 as a recovery set that can rewrite
   set 11. Rotating only 11 leaves a back door whose key NXP holds: "it is
   required that key set 12 shall be changed to a customer defined and owned
   value before the SE051 product is deployed in production."
2. **`osk_se050_require_scp()`**, which sets `SCP_REQUIRED` via
   `SetPlatformSCPRequest` (AN12413 4.6.2). The chip ships as
   `SCP_NOT_REQUIRED`. Rotating the keys while the channel is not required at
   all accomplishes very little — the applet would still answer commands that
   arrive with no channel.

Both are in the contract header (`osk_se050.h`) rather than in some later
stage, because a device that has already shipped cannot be hardened
retroactively.

### What is spec-exact here and what is not

The *contents* of the command are exact and derived from the published
specifications: the PUT KEY data field follows GPCS Table 11-67 and
Amendment D Table 7-10, each new key is wrapped with the **old** set's Key-DEK
using AES-CBC with a zero ICV (Amendment D 6.2.8), and the key check value is
the first three bytes of AES(new key, sixteen 0x01 bytes) per Amendment D
7.2.2. A test asserts that no new key appears in the clear anywhere in the
command.

What is **not** confirmed is the *level* the command has to travel on. This
driver opens the applet-level AESKey session (AN12413 4.5.3: `CLA 0x80 INS
0x50` after selecting the applet). Platform SCP sits one level below, at the
card manager, and AN12413 documents only applet commands. AN12973 points at
`se05x_RotatePlatformSCP03Keys` in NXP's middleware for an example — vendor
code, which was not read. So it may need its own session with key version 11
instead of 00 and with no applet selected. The SCP03 layer can do that; it is
not tied to a level. What is missing is confirmation of which level it is, and
on hardware that is a one-command measurement: send it and see whether 0x9000
comes back. This is flagged in the code at the call site as well.

## The PIN is an AESKey authentication object, not a UserID

`osk_se050_pin_tries_left()` works and reports a real number. Getting there
took a rebuild of the PIN path, decided by the master thread.

The first version stored the PIN as a UserID object. That works for checking
a PIN, but AN12413 section 3.2.4.4 states plainly that for objects of type
UserID the failed-attempt counter **is not reported** — it reads 0 even on an
attested read, and the errata sheet lists the same as APP.3. The counter still
*worked*; it just could not be read.

That was not good enough, and the reason is in `docs/threat-model.md`: the
promise there is that the retry counter sits in the SE050 and therefore cannot
be bypassed by wiping the flash. A counter the chip keeps but will not hand
over only carries half of that promise — the lockout would then depend on the
firmware counting along, and firmware is exactly what the SE050 does not
protect against. On top of that, CTAP2 requires `authenticatorClientPIN` to
report the remaining attempts via `getPINRetries`, so the alternative was to
have the CTAP layer invent a number.

So the PIN is now an **AESKey authentication object** (`P1_AES`,
`INS_AUTH_OBJECT`, with `TAG_MAX_ATTEMPTS`), for which the chip does report the
counter.

**How checking works now.** The key is derived from the PIN on the host with
AES-CMAC over a fixed label, and verifying the PIN means opening an AESKey
session against the PIN object. If the session comes up, the PIN was right —
the proof is the card cryptogram, which only matches with the right key. The
comparison therefore happens *in the chip*, the host learns only yes or no,
and the chip counts the failures itself. The session is closed again
immediately: it is only the proof, no rights hang off it, and the chip holds
at most two sessions (AN12413 Table 16) — one of which is the device channel.

A slow KDF (PBKDF2, Argon2) would be pointless here: the derived key can only
be tried *against the chip*, which counts and locks after eight attempts.
There is no ciphertext anyone could grind offline. The derived key lives in
nRF52840 RAM only for the duration of the check and is wiped after.

**Reading the counter** needs an attested read: `INS_READ | INS_ATTEST` with a
signing key, an algorithm and 16 bytes of freshness (AN12413 3.2.7.2). The
attributes come back in `TAG_2`, where the attempt counter sits at offset 6 and
the maximum at offset 12 — both before the variable-length policy field, so
fixed offsets are correct. The attestation signature is deliberately *not*
verified: the answer already arrives through the SCP03-protected channel, so
attestation here is merely the way to reach the attributes, not the protection.
This needs one EC key pair with `POLICY_OBJ_ALLOW_ATTESTATION`, created at
setup (`OSK_ATTEST_KEY_ID`).

The contract signatures of `osk_se050_pin_verify`, `osk_se050_pin_set` and
`osk_se050_pin_tries_left` did **not** change.

## What the chip still cannot do: `osk_se050_key_derive_transient()`

It returns `OSK_ERR_UNSUPPORTED`, and this is a finding about the chip rather
than unfinished work.

The contract asks for exactly the right thing — derive a per-service key pair
inside the chip, private part never leaving. **The SE05x cannot do it.** Its
only derivation commands are HKDF (AN12413 4.14.1) and PBKDF2 (4.14.2), and
both return the derived material in `TLV[TAG_1]` of the response, i.e. to the
host. There is no command that places a derived key pair into an object
inside the chip, and `WriteECKey` (4.7.1.1) only ever takes the private value
as input from the host via `TAG_3`.

The obvious route — HKDF out, then `WriteECKey` back in — walks the private
key through the nRF52840, whose read protection this project treats as broken
(`docs/architecture.md`). That is precisely the guarantee we cannot keep, so
the driver refuses rather than offering a function that looks safe and is not.

This matters beyond this file: `docs/architecture.md` currently states that
"every FIDO credential, SSH key and wallet address is derived from it inside
the chip". On an SE05x that sentence does not hold.

**What about `ExportObject` / `ImportObject`?** This looked like the answer
and it is not. It was proposed here, adopted, and then checked properly — see
the next section for why it does not work. The short version: an exported
object can only be imported back into the *same* chip, and only while its
object slot still exists there, so it offloads nothing.

Choosing between those is an architecture decision for the master thread and
the CTAP strand, not for this driver. It is reported.

## Export/Import does not offload credentials — correcting my own proposal

An earlier version of this file suggested `ExportObject` / `ImportObject` as
the way to get one key per service without filling the chip. **That was wrong,
and this section is the correction.** Three facts from AN12413 section 3.2.8,
read after the idea had already been adopted:

1. **Only transient objects can be exported.** Persistent ones cannot.
2. **The wrapping keys are the chip's own.** "The secure element holds a
   randomly generated persistent 256-bit AES key and an 128-bit AES CMAC key.
   Both keys do not require user interaction, they are internal to the SE050."
   There is no way to choose, supply or negotiate that key.
3. **The object must still exist to import it back.** "An object may only be
   imported into the store if the SecureObject ID and type are the same as the
   exported object. Therefore, it is not possible to import if the
   corresponding object in the applet has been deleted."

Point 3 is the one that kills the idea. And a transient object's *attributes*
are stored persistently anyway (3.2.2.2), so each credential still costs its
slot in the chip whether or not its value is parked on the host. Export/Import
is a way to carry a transient value across a deselect, not a way to store
credentials outside the chip.

### What "this device only" should actually be

No new mechanism is needed, and no new wrapped-key API. One persistent EC key
pair per credential, created inside the chip with `WriteECKey` and no key
material, used with `osk_se050_sign()`, deleted with `osk_se050_key_delete()`.
The private part then never exists outside the chip at all — which is a
*stronger* guarantee than the Export/Import route would have given, because
there is no blob to steal and no unwrap step.

The real limit is chip memory, not the mechanism: SE051C2 has 104 kB of user
memory and each object costs its attributes plus the key. So the device has to
be able to ask, and now it can: **`osk_se050_free_memory()`** wraps
`GetFreeMemory` (AN12413 4.19.3) for persistent memory, so the setup wizard and
the UI can warn before the limit instead of discovering it by failing to create
a key.

Two honest limits on that number, both passed through rather than papered over:

- The chip reports **`0x7FFF` for anything at or above 32768 bytes** and will
  not say more. On a fresh SE051C2 with 104 kB the answer is therefore simply
  "plenty", and it only becomes a real figure once the chip is more than half
  full. That is exactly when a warning matters, so it is good enough — but it
  is a lower bound, not a measurement.
- The granularity is 16 bytes and the applet reports the worst case
  (AN12413 4.19.3). Good enough to warn, not good enough to divide by an
  object size and print "41 services left".

A reply of only one byte is rejected as `OSK_ERR_FORMAT` rather than read as
zero: otherwise a misunderstood answer would show up as "chip full".

### Can a root secret be mirrored to a second device?

**Not out of the chip.** Asked and answered from the documents:

- `ExportObject` cannot do it: chip-internal keys only, same-chip import only,
  and only while the object still exists (above).
- `ReadObject` cannot do it either: "If the object is a private key or a
  symmetric key or a userID, the command will return an error" (4.7.3.1).
- `ImportExternalObject` (4.7.2) runs the other way — host into chip.

So there is no documented path by which a secret leaves an SE05x, under a
negotiated key or any other. For two devices to hold the same root secret, it
has to be **generated outside both chips** — on the host during pairing — and
written into each with `WriteSymmKey`, or imported into each with
`ImportExternalObject` under an ECKey session.

That is exactly the cost already named for the "mirrored" profile: the secret
is briefly in nRF52840 RAM. The point worth being precise about is *when*: not
when mirroring an existing device, but when the secret is first created. A
device whose secret was born in the chip can never be mirrored afterwards.
So the choice of profile has to be made **at setup, before the secret exists**,
and cannot be changed later. That belongs in the setup wizard, and it is the
one place where "mirrored" and "this device only" genuinely diverge.

> **Two more numbers from the same table**, both of which settle open points
> elsewhere: user memory is **46 kB to 104 kB** depending on configuration —
> that is the range behind the "50 or 104 kB" contradiction — and **Deep
> Power-Down below 5 µA is present on both variants**, while the ordinary
> power-down mode ships **disabled** and must be enabled through the Perso
> applet.
>
> What stays true below: a **FIPS-configured** part behaves as described, and
> `osk_se050_curves()` reading the bitmap instead of assuming is still the
> right design. The error was calling that configuration "a real SE051" as
> though it were the only one.

The FIPS security policy prints the feature bitmap of an actual certified
SE051: **`0x27F2`**. Decoded against AN12413 Table 5:

| on | off |
| --- | --- |
| ECDSA/ECDH/ECDHE, HMAC, RSA plain, RSA CRT, AES, DES, PBKDF2, TLS, I2C master | ECDAA, **EdDSA**, **DH_Mont**, MIFARE, **FIPS_MODE_DISABLED** |

Three consequences, and none of them is theoretical:

1. **No Ed25519 and no X25519** on that configuration. `osk_se050_curves()`
   already reports this correctly, because it reads the bitmap instead of
   assuming — but anything built on those curves (SSH keys, wallet) would
   have nothing to stand on.
2. **ECDH is refused outright.** `CONFIG_FIPS_MODE_DISABLED` being 0 means
   the part may run in FIPS mode, and AN12413 section 4.10.3.1 is explicit:
   "When CONFIG_FIPS_MODE_DISABLED is not set, this function will always
   return SW_CONDITIONS_NOT_SATISFIED." So `osk_se050_ecdh()` cannot work on
   such a part at all. The driver now checks the bit and returns
   `OSK_ERR_UNSUPPORTED` rather than letting a bare "denied" come back, which
   would look like a missing PIN rather than a chip that cannot do it.

   **What this costs is worth stating precisely**, because it is easy to
   overstate. Pairing a second device does *not* depend on it: the root
   secret for the mirrored profile is created on the host anyway and written
   into both chips, so in-chip ECDH was a convenience for protecting that one
   transfer, and a key exchange in firmware is tolerable for a transport key
   that lives for a single pairing — the secret is in nRF52840 RAM at that
   moment regardless, which is the known and accepted price of that profile.

   What is genuinely lost is the server-to-server case: `docs/threat-model.md`
   promises that a copied server has no identity because "the node key stays
   in the SE050". That key is meant to live in the chip for years and have
   X25519 computed there, precisely so a copy of the server does not carry it.
   Move that into firmware and the promise is void. On a FIPS part this use
   case is simply unavailable, and the software has to say so rather than fail
   with something that looks like a missing PIN.
3. **HMAC is on** — which is the good news, and the same answer the purchase
   question needed: the root secret can be stored as an HMACKey.

**This is one configuration, not necessarily the one being ordered.** AN12973
Table 3 says the SE051C2 *variant* supports Ed25519, Curve25519 and RSA. The
feature bitmap is set per configuration at the factory and cannot be changed
afterwards ("It is not possible to modify the applet version or the supported
features bitmap after the device leaves the factory"). So this is a thing to
check on the delivered part, early — `osk_se050_open()` reads the bitmap, so
one run answers it — and a thing the purchase decision should be aware of,
because a FIPS-mode part would quietly remove three capabilities the design
assumes.

## Deliberate limits

These are choices, not omissions:

- **No exportable keys.** `osk_key_policy_t.exportable` is in the contract so
  the caller can see it, but asking for it returns `OSK_ERR_UNSUPPORTED`
  rather than being silently ignored. A promise the device is not meant to
  keep should be refused, not quietly dropped.
- **`needs_touch` is not handled here.** The SE050 cannot read a button. The
  press is required before `osk_se050_sign()` is called, by the display and
  approval layer.
- **Security level is fixed at the maximum** (`0x33`: command and response
  both encrypted and authenticated). A lower level is not offered, because it
  would be a setting someone eventually sets wrong.
- **No extended-length APDUs.** The chip supports them; the longest command
  here is a 97-byte P-384 public key, so they are not needed and not written.
- **No multi-step MAC or cipher.** `MACInit`/`Update`/`Final` exist on the
  chip; nothing in this device needs them, so messages over the one-shot
  limit are rejected rather than truncated.
- **DESFire, TLS-PRF and I2C-master mode are absent**, including their
  constants. An unused constant never gets proof-read. RSA used to be in
  this list and no longer is: strand A implements it, so its constants are
  now sent and therefore worth proof-reading. See the RSA section below.

## Chip variant: SE051C2

The hardware strand settled on **SE051C2** (test board MIKROE-5392), not
SE050C2. Nothing in this driver is nailed to the SE050:

- The applet AID, the APDU format and every constant used here come from
  AN12413, which NXP applies to the SE05x family; AN12973 describes the SE051
  variants as differing at applet and configuration level, not in the command
  set.
- The driver asks the chip what it can do rather than assuming: `curves()`
  reads `ReadECCurveList` and the feature bits out of `VersionInfo`, so a
  variant with different curves reports differently without a code change.
- The larger user memory (104 kB instead of 50 kB) needs nothing here — this
  driver stores nothing by itself.

### The applet is a different version from the one AN12413 describes

This driver is built on AN12413 Rev. 2.12, which states it covers applet
versions **3.1.0, 3.1.1 and 3.6.0** — those are SE050 applets. AN12973
Table 4 says an SE051C2 ships with applet **7.2** (OEF ID A8FA, date code
≥ 2201) or **6.0** (OEF ID A564, ≤ 2152).

The SE051 has its own APDU specification, **AN12543 "SE051 IoT Applet APDU
Specification"** (AN12973 reference [1]). It is behind an NXP account login
and could not be downloaded. Since the frame layer moved to GlobalPlatform,
**this is the only document still missing.** Unlike the frame layer, no
freely published equivalent exists that would replace it — but two free
sources have narrowed what it would still settle, as described above: the
FIPS policy fixes the AID, the `VersionInfo` layout and `P2_VERSION_EXT`,
and NXP's own middleware shows the SE051 support built on the 3.x layer.

**How much this matters has narrowed a long way**, from two free sources.

First, NXP's own middleware (github.com/NXP/plug-and-trust, BSD-3-Clause)
keeps its APDU code in a directory named `se05x_03_xx_xx` — the 3.x layer
that AN12413 describes — and switches on a single macro,
`SSS_HAVE_SE05X_VER_GTE_07_02`, at roughly 27 places across the APDU
headers. **NXP builds SE051 support on top of the 3.x APDU layer.** So this
driver is not standing on the wrong foundation; the differences are countable
rather than unbounded. That was established by counting occurrences and file
names only — the clone was deleted afterwards and no vendor code was read
into this driver. The result is kept as a list of locations (no code) outside
the repository.

Second, the FIPS security policy confirms three things directly, on a real
part running applet 6.0.0:

- **The applet AID is byte-identical**: `A0000003965453000000010300000000`,
  selected with `CLA 00, INS A4, P1 04, P2 00, Lc 10`. The open question of
  whether the AID changed on SE051 is answered: it did not.
- **The `VersionInfo` layout is as implemented.** The documented answer is
  `06 00 00 27 F2 FF FF` — three version bytes, then the two feature bytes,
  then two more. This driver reads the feature bitmap from bytes 3 and 4,
  which is right.
- **`P2_VERSION_EXT` is `0x21`.** AN12413 section 4.19.1 names that parameter
  but its constant table (Table 23) omits the value; the FIPS policy prints
  the full command, `80 04 00 21`.

What remains unconfirmed is narrower than before: not "the command set might
be different", but "at a countable number of places it can differ, and
AN12543 is where they are written down". Every constant in `se050_cmd.h` is
documented for 3.x and, on this evidence, very likely correct for 7.2.

What limits the damage: `osk_se050_open()` reads `VersionInfo` from the
applet-select response, so the applet version is known at runtime and a
mismatch surfaces at startup rather than halfway through a signing operation.

A second consequence of Table 4: the two OEF IDs have **different factory
SCP03 keys** (AN12973 Table 6 lists A8FA and A564 separately). Commissioning
has to select the key set by OEF ID — one more reason those values are not
compiled in.

### Still unverified for SE051C2

The applet AID is now confirmed from the FIPS policy, so what remains is the
behaviour of applet 7.2 at the places AN12543 would describe, and the feature
bitmap of the delivered part. `osk_se050_open()` reads both the version and
the bitmap at startup, so one run on real hardware settles them — but that
run has not happened, because there is no chip.

## Secrets

- The nRF52840 never holds a secret for longer than one operation. Its read
  protection has been defeated with voltage glitches in the past, so it is
  treated as readable.
- Every buffer that held key material is cleared with `osk_wipe()`, which
  goes through a `volatile` pointer so the compiler cannot delete the clear.
- MACs and cryptograms are compared with `osk_memeq_ct()`, in constant time.
  An early exit would leak how many bytes matched.
- Nothing secret is ever logged. Status words from the chip are translated
  into `osk_result_t` and never passed through, so a chip error code cannot
  become a hint in a log file.

## RSA: 2048, 3072, 4096 (strand A, 28 October 2026)

Five contract functions are written and compile: `osk_se050_rsa_sizes()`,
`_rsa_key_create()`, `_rsa_public()`, `_rsa_sign()`, `_rsa_decrypt()`, in
`src/classes/se050/se050_rsa.c`. PC tests in `test/se050/test_rsa.c`. **Level
2 of four** — written / compiled / in the image / run on the device. Nothing
has run on hardware.

Constants come from AN12413 Rev. 2.12: RSASignatureAlgo (Table 31),
RSAEncryptionAlgo (Table 32), RSABitLength (Table 33), RSAKeyComponent
(Table 34), `P1_RSA` (Table 22), `P2_RAW` and `P2_DECRYPT_ONESHOT`
(Table 23), `CONFIG_RSA_PLAIN` / `CONFIG_RSA_CRT` (Tables 5 and 40).

> **On reading those tables.** `se050_cmd.h` already warns that the PDF text
> extraction separates the name and value columns, so names and values land
> as two lists rather than as pairs. Every value above was taken by aligning
> the two lists and then checked against values already in the header that
> were verified earlier (`P1_AES` 0x03, `P1_HMAC` 0x05, `P1_CURVE` 0x0B,
> `P2_SIGN` 0x09, `P2_DH` 0x0F, `P2_RANDOM` 0x49, `P2_SCP` 0x52,
> `TYPE_AES_KEY` 0x09 and five more). All of them land where the alignment
> predicts. One further self-check: Table 40 gives `CONFIG_RSA_ALL = 0x0060`,
> which is exactly `CONFIG_RSA_PLAIN | CONFIG_RSA_CRT` = `0x0020 | 0x0040`.

### What `rsa_sizes()` asks the chip, and what it does not

It reads `CONFIG_RSA_PLAIN` and `CONFIG_RSA_CRT` out of the feature bitmap
that `osk_se050_open()` already fetched. Zero means the part cannot create
RSA objects at all — the SE051A2 case, which answers on the same I2C address
as the C2. The firmware learns this at startup instead of failing on the
first key.

**The limit of that query belongs in the same breath: the chip says
*whether*, not *which lengths*.** For curves there is `ReadECCurveList`
(AN12413 4.8.4); for RSA lengths there is no command. The three lengths the
function reports come from Table 33 plus section 4.7.1.2 ("Other values are
not supported") — a citation, not a measurement of the delivered part. The
measurement is the OEF ID: **A8FA or A564 = C2 (right), A920 or A565 = A2
(wrong)**, per the table earlier in this document.

### CRT or raw is decided by the chip, not by us

`WriteRSAKey` (4.7.1.2) creates either a CRT-format or a raw-format key, and
"once an RSAKey object has been created, its format remains fixed". The
driver uses CRT (`P2_DEFAULT`) where `CONFIG_RSA_CRT` is set, because CRT
signing is faster and that matters for 4096 bits on a chip behind an I2C bus;
with only `CONFIG_RSA_PLAIN` it falls back to `P2_RAW`, which AN12413 permits
only for generating a key pair on the chip. No key component is ever sent, so
the private half is created inside the chip and never comes out.

### Finding: OAEP cannot be honoured as the contract describes it

`OSK_RSA_PAD_OAEP` returns `OSK_ERR_UNSUPPORTED`, and this is a finding about
the chip and the contract together, not unfinished work.

AN12413 Table 32 lists exactly one OAEP variant: `RSA_PKCS1_OAEP`, "RSAES-
OAEP (using SHA1 as digest)". There is no OAEP-SHA256. The contract's
`osk_hash_t` offers SHA-256, SHA-384 and SHA-512 and no SHA-1, so **there is
no value of `hash_alg` for which an OAEP call would be correct.** Quietly
using SHA-1 would compute a different padding from the one the caller
ordered — the kind of error that only shows up when the other side tries to
unwrap the message.

What this does **not** cost: PIV slot 9D and the OpenPGP encryption key both
decrypt with PKCS#1 v1.5, which works. What stays open: whether the SE051
applet (6.0 or 7.2) adds OAEP with a modern digest. That would be in AN12543,
which is behind an NXP login.

A second, smaller one: `OSK_RSA_PAD_NONE` works for *decryption*
(`RSA_NO_PAD`, Table 32) but not for *signing* — Table 31 has no entry
without padding. Raw signing is refused rather than rebuilt out of the
decrypt command, which would mean writing a signature operation in this
repository.

### What had to change underneath: extended-length APDUs

**An RSA ciphertext is as long as the modulus** — 256 bytes at 2048 bits, 512
at 4096 — so the decrypt command does not fit in a one-byte Lc. Until now the
driver refused anything over 255 bytes, with the comment that the longest
command was a 97-byte P-384 public key. That was true and is no longer.

So `se050_apdu.c` and `se050_scp03.c` now build the ISO 7816-4 extended form
(`00 Lc_hi Lc_lo`, two-byte Le) whenever the payload passes 255 bytes. The
short form is byte-for-byte unchanged below that, which is why the 902 older
checks still pass untouched.

AN12413 section 4.1 states plainly that the applet accepts both forms: "Both
standard as well as extended length APDUs are supported." **That is a
citation, not a measurement** — the same standing as the frame values in
`se050_t1_wire.h`, and it is marked as such at both call sites. On hardware
it is one experiment: send an RSA decrypt and see whether `0x9000` comes
back.

The response direction needed nothing: a response carries no Lc, and the
driver already announces `SE050_IFSD = 1024`, so a 512-byte modulus arrives
in one block.

### What the PC tests do and do not show

`test_rsa.c` runs against `se050_sim.c`, which now keeps real RSA objects
rather than replaying a canned answer. That makes two things checkable that
a canned answer cannot show:

- the public exponent comes back **three** bytes long, not four, so code that
  assumed four would fail the test rather than build a wrong certificate
  later;
- a 4096-bit decrypt really travels: 512 bytes in, through the extended
  header, chained into I-blocks at the simulated IFSC of 254, reassembled on
  the other side.

The standing caveat from "Verified only against itself" applies in full:
driver and stand-in read AN12413 the same way, so if both misread the same
sentence they still agree.

## Monotonic counters (strand A, 28 October 2026)

`osk_se050_counter_create()`, `_counter_read()` and `_counter_raise()` are
written and compile, in `src/classes/se050/se050_counter.c`, with PC tests in
`test/se050/test_counter.c`. **Level 2 of four.** There is deliberately no
`counter_set()` and no `counter_delete()`: either would be a way back, and
then the counter would not be a counter.

### The numbers, with citations

The plan names AN13187 as the source. **That document is not available here**
— the local document folder holds AN12413, AN12973, the data sheets, the
errata sheet, the GlobalPlatform specifications and the FIPS policy, but not
AN13187. Everything the driver sends is fully documented in AN12413, so the
numbers below are cited from there, and the gap is recorded rather than
papered over.

| Quantity | Value | Where it says so |
| --- | --- | --- |
| Counter length | **1 to 8 bytes**; this driver creates 8 | AN12413 4.7.1.6, `TLV[TAG_2]`: "2-byte counter size (1 up to 8 bytes)" |
| Granularity | **1** — a write without a value increments by one | AN12413 4.7.1.6, `TLV[TAG_3]`: "if not present, increment by 1" |
| Direction | forward only | 4.7.1.6: "Counters can only be incremented, not decremented." |
| Upper value | `0xFFFF_FFFF_FFFF_FFFF` at 8 bytes, and then it stops | 4.7.1.6: "When a counter reaches its maximum value … it cannot be incremented again." |
| Cost per counter | **92 bytes + counter length** of NVM = **100 bytes** at 8 bytes | AN12413 Table 288 (section 8.1, "Secure Object memory File objects") |
| Maximum number of counters | **no documented limit** | AN12413 Table 16 lists `MAX_NUMBER_OF_SESSIONS` and the APDU sizes and names no counter limit |

**So the answer to the question strands B and D asked — one counter per
access, or one shared — is: one each is possible, and the limit is memory,
not a count.** User memory is 46 kB to 104 kB depending on configuration
(AN12973 Table 4, quoted earlier in this document). At 100 bytes that is
roughly 470 to 1060 counters *if nothing else were stored* — which is an
upper bound and not a budget, because keys live in the same memory. The
runtime answer is `osk_se050_free_memory()`, which reports the real figure
(and saturates at `0x7FFF`).

Eight bytes was chosen because the contract carries `uint64_t`. Any shorter
length would be a silent ceiling that only shows up on overflow.

### Three things the implementation does that are not obvious

1. **`raise()` reads before it writes.** Three reasons, and none is
   droppable. It makes the call repeatable, which the caller needs after a
   power cut in the middle of a write — it does not know whether the command
   arrived. It avoids the chip answering an error for a value below the
   current one, which would look like a fault although the state is right.
   And it reads the counter's **length**, because `TLV[TAG_3]` "must always
   have the same length as the existing counter; otherwise the command will
   return an error" — a counter somebody else created with four bytes is then
   still served correctly.
2. **`create()` checks first whether the counter exists**, and returns
   `OSK_ERR_EXISTS` if it does. This is the trap in 4.7.1.6: a `WriteCounter`
   without `TAG_3` against an **existing** counter means "increment by one".
   A setup routine that ran twice would have moved the vault's rollback
   protection by one, silently.
3. **The initial value is not claimed.** AN12413 does not state what a
   freshly created counter starts at. `create()` therefore asserts nothing;
   whoever needs the starting value reads it. `raise()` does not care,
   because it reads first. (The stand-in starts at zero, which is what one
   would expect — but a stand-in is not a document.)

### The test that matters: across a restart

`test_counter.c` closes the driver, re-attaches the stand-in **without
clearing its state**, and opens again. The chip keeps its objects, the driver
loses everything. The counter still reads 42, and still refuses to go back to
7.

A test that only counts inside one run would not show the failure that
matters — a counter living in nRF52840 RAM would start at zero on every
insertion and pass such a test.

## Findings about the contract (`osk_se050.h`), reported to the master

The header is the contract and was not changed. These three are reported
instead.

1. **`osk_se050_counter_raise()` describes two different behaviours for the
   same case.** One paragraph says: if the counter already stands at the
   value or higher, nothing changes and the result is still `OSK_OK` — which
   is what makes the call repeatable. The next says: "Ein kleinerer Wert ist
   keine Aenderung und kein Fehler des Chips, sondern einer des Aufrufers,
   und wird als solcher gemeldet" — reported as a caller error. For
   `at_least < current` those two give opposite results, `OSK_OK` against an
   error. **Implemented as `OSK_OK`**, because repeatability after a power
   cut is the stated purpose and the master's brief repeated that sentence.
   The second sentence should probably be narrowed to the one case it does
   fit: a target value that does not fit in the counter's byte length, which
   *is* a caller error and is reported as `OSK_ERR_ARG`.

2. **`osk_se050_rsa_decrypt()`'s `hash_alg` has no usable value for OAEP.**
   See the OAEP finding above. The contract says `hash_alg` applies only to
   OAEP; the chip's only OAEP is SHA-1; `osk_hash_t` has no SHA-1. Either
   `osk_hash_t` gains SHA-1 for this one use, or OAEP stays refused. Refusing
   costs nothing today: PIV and OpenPGP both use PKCS#1 v1.5.

3. **Parts 1 of strand A was already done.** `osk_se050_rotate_scp_keys()`
   and `osk_se050_require_scp()` were already implemented and tested before
   this strand started — see "The factory keys are published" above, written
   by the earlier se050 session. The gap the brief described as "a real hole
   today" is closed in code at level 2. What is still genuinely open there is
   recorded in that section and unchanged: **which level the `PUT KEY`
   command has to travel on**, applet or card manager. On hardware that is
   one command.

   One thing worth stating plainly, because the contract leaves it to the
   caller: `rotate_scp_keys()` takes a `key_version`, so **replacing both key
   set 11 and key set 12 is two calls, and nothing in the driver enforces the
   second one.** Rotating only 11 leaves the recovery set with a key NXP
   holds. The commissioning routine — which is not in this folder — has to
   make both calls and `require_scp()`, and should treat a partial run as a
   failure. That belongs in whichever strand owns first-run commissioning,
   and it is the one place where this part can still be got wrong.

## SCP11 to the card: not built, and why

The plan lists "SCP03/SCP11 to the card" under strand A. **SCP11 is not
built, deliberately, and this is a finding rather than a missing piece of
work.**

SCP11 would be the mutually authenticated channel to the microSD counterpart
— a different case from Platform SCP03, which protects the I2C line to the
SE051. It depends on three decisions that are not made:

1. **Which operating mode the carrier runs in.** `docs/datentraeger-konzept.md`
   describes three (this stick only, with a card word, sealed only), and they
   differ precisely in how — and whether — the data key is wrapped. A channel
   built for one of them would be wrong for the others.
2. **Whether there is a counterpart that can speak SCP11 at all.** The card
   is read only in our own sticks, so the peer is another openSecureKey, and
   what runs on it is this same firmware. Which end holds which certificate,
   and where the key pairs come from, is part of the carrier design, not of
   this driver.
3. **Whether the delivered chip can do the key agreement.** SCP11 rests on
   ECDH, and a FIPS-configured SE051 refuses ECDH outright (AN12413 4.10.3.1,
   see the section above). On such a part SCP11 cannot be built at all. That
   is settled by reading the feature bitmap of the delivered chip — one run of
   `osk_se050_open()`.

Building it now would mean guessing all three. The decision belongs to the
master and to whoever owns the carrier; the driver's SCP03 layer is not tied
to one level or one key set, so it is not in the way.
